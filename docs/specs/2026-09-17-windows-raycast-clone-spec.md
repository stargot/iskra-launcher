## 1. Резюме (TL;DR)

Строим лончер-аналог Raycast для Windows 11: по глобальному хоткею всплывает
лёгкое окно с мгновенным fuzzy-поиском по приложениям, файлам, настройкам и
командам. В MVP входят клипборд-история, сниппеты, базовое управление окнами и
система плагинов с SDK. Стек: **Tauri 2 (Rust-ядро) + TypeScript/React в
WebView2**; плагины выполняются в **отдельных процессах** и общаются с ядром по
JSON-RPC over stdio. Ключевые целевые показатели: отклик окна по хоткею < 100 мс,
RAM в простое ≤ 80 МБ, инсталлятор ≤ 20 МБ.

## 2. Проблема и контекст

### 2.1. Текущая ситуация

На Windows нет доминирующего аналога Raycast. Рынок фрагментирован:

- **PowerToys Run** — бесплатный, но базовый: слабая расширяемость, нестабильный
  UX, нет экосистемы.
- **Flow Launcher** — функциональный и открытый, но WPF-UI устаревает, плагины
  только на C#, UX заметно ниже эталона.
- **uTools, Cerebro** — закрытые либо ориентированы на другие рынки.
- **Raycast** — эталон категории (мгновенный UX, декларативный API плагинов,
  store), но существует только на macOS; Windows-версии нет.

Ниша «мгновенный + лёгкий + расширяемый + красивый» на Windows пуста.

### 2.2. Бизнес-потребность

- **Аудитория:** power users и разработчики на Windows — растущий сегмент
  (кросплатформенные команды, уход с macOS, WSL-разработка).
- **Модель (гипотеза, проверяется позже):** freemium как у Raycast — ядро
  бесплатно, облачная синхронизация/командные фичи/темы — платно.
- **Конкурентное преимущество:** производительность уровня нативных приложений
  (Tauri/Rust), которой нет ни у одного из существующих аналогов, плюс
  JS/TS-экосистема плагинов — самая массовая.

## 3. Цели и анти-цели

### 3.1. Что в scope (MVP)

- Глобальный хоткей (по умолчанию `Alt+Space`) → мгновенное появление окна;
  скрытие при потере фокуса; корректное поведение поверх fullscreen.
- Fuzzy-поиск: установленные приложения (Start Menu), файлы в папках
  пользователя, настройки Windows (ms-settings:), встроенные команды.
- Встроенные команды: калькулятор/конвертер, системные действия
  (lock/sleep/restart/выключение монитора), fallback-поиск в интернете.
- Клипборд-история: текст и изображения, поиск, pin, переживает перезагрузку.
- Сниппеты: вставка выбранного сниппета из лончера.
- Управление окнами: left/right half, maximize, move to next monitor, center.
- Система плагинов: SDK `@iskra-launcher/sdk` (JS/TS), изоляция процессов, модель
  разрешений; 5–8 first-party плагинов (npm search, GitHub, emoji, перевод,
  kill-process и др.).
- Автозапуск, иконка в трее, настройки (переназначение хоткеев, тема,
  исключения индексации).

### 3.2. Что НЕ в scope (анти-цели)

- macOS и Linux (архитектура это допускает, но MVP — только Windows 11).
- Облачная синхронизация настроек/клипборда, командные фичи.
- Магазин плагинов с модерацией (в MVP — установка из git-репозитория +
  курируемый community-список).
- AI/LLM-фичи (отдельный этап после MVP).
- Авто-подстановка сниппетов при наборе текста (text expansion) — только вставка
  из лончера.
- Замена PowerToys целиком (не дублируем FancyZones и пр.).

## 4. Предлагаемое решение

### 4.1. Обзор архитектуры

```
iskra.exe — shell (Tauri 2, Rust)
│
├── UI (WebView2): React + TypeScript
│     окно лончера: список результатов, формы, превью, настройки
│        ▲  Tauri IPC (JSON)
│        ▼
└── Core (Rust)
      ├── hotkey service — RegisterHotKey, показ/скрытие окна
      ├── search engine — fuzzy-ранжирование, агрегация провайдеров
      ├── indexers — приложения (Start Menu), файлы, настройки Windows
      ├── clipboard manager — AddClipboardFormatListener, история в SQLite
      ├── window manager — DWM / SetWinEventHook
      └── storage — SQLite (клипборд, сниппеты, кэш индексов, настройки)

extension host — отдельный процесс (Node.js)
      ▲  JSON-RPC over stdio: инициализация, запросы, сериализованное UI-дерево
      ▼
   плагины — по процессу на плагин (изоляция сбоев и разрешений)
```

**Поток данных запроса:** нажатие клавиши → UI отправляет запрос в core →
core параллельно опрашивает индексы в памяти и активных плагинов → агрегация и
ранжирование → возврат списка в UI. Плагины отвечают асинхронно; UI не ждёт
медленных провайдеров (результаты дописываются по мере поступления).

### 4.2. Ключевые проектные решения

**Решение 1: Оболочка — Tauri 2, а не Electron**
- **Контекст:** лончер — резидентный процесс 24/7; память, вес дистрибутива и
  скорость старта — конкурентные характеристики продукта.
- **Варианты:** (a) Tauri 2 + WebView2, (b) Electron + React (путь Raycast),
  (c) WinUI 3 / WPF, (d) Flutter Desktop.
- **Выбор:** Tauri 2.
- **Обоснование:** бинарник ~5–10 МБ и RAM уровня нативных приложений против
  ~150+ МБ у Electron; WebView2 (Chromium) предустановлен в Windows 11; прямой
  доступ к WinAPI через крейт `windows-rs` без прослойки Node; веб-стек даёт
  быструю разработку сложного UI (списки, анимации, acrylic/mica).
- **Последствия:** нужна Rust-компетенция в команде; на Windows 10 без WebView2
  потребуется bootstrapper (MVP — только Win11, где WebView2 гарантирован);
  Electron остаётся запасным вариантом, если ограничения WebView2 заблокируют
  ключевые UX-сценарии.

**Решение 2: UI — React + TypeScript**
- **Контекст:** UI лончера — один «умный» список, формы и превью; важна
  скорость разработки и доступность кадров.
- **Варианты:** (a) React, (b) SolidJS, (c) Svelte.
- **Выбор:** React.
- **Обоснование:** крупнейшая экосистема, совпадение с DX плагинного SDK
  (см. решение 4), узкое место лончера — не производительность фреймворка.
- **Последствия:** минимальный оверхед рантайма React — приемлем; переход на
  Solid при необходимости — локальная оптимизация.

**Решение 3: Плагины — out-of-process хост, JSON-RPC over stdio**
- **Контекст:** плагины сторонних разработчиков не должны ронять лончер,
  тормозить UI и получать доступ ко всему; при этом экосистема должна
  опираться на массовый язык.
- **Варианты:** (a) плагины в процессе приложения (Electron-way, Node API),
  (b) встроенный JS-рантайм (QuickJS/boa в Rust), (c) отдельные процессы
  с JSON-RPC.
- **Выбор:** (c) — каждый плагин/группа плагинов в отдельном процессе;
  reference-хост на Node.js; протокол — JSON-RPC over stdio.
- **Обоснование:** изоляция сбоев (бесконечный цикл в плагине лечится
  таймаутом+kill, а не падением лончера); языко-агностичный протокол (JS
  сегодня, Python/Rust завтра); простой контроль разрешений (хост проксирует
  сеть/клипборд/ФС и проверяет permissions); доступ к npm-экосистеме.
- **Последствия:** старт плагина: замер фазы 0 дал 46 мс avg / 54 мс p95 (лучше
  ожидаемых 100–300 мс) — прогрев нужен минимальный. Node-рантайм **не бандлим**:
  требуем установленный Node с понятным онбордингом; SEA (Node 22) — запасной
  путь, замер дал +87,5 МБ к бинарнику — несовместимо с лимитом «инсталлятор
  ≤ 20 МБ» (§7, вопрос закрыт 2026-09-29).

**Решение 4: UI плагинов — декларативное дерево, а не webview на плагин**
- **Контекст:** плагины Raycast ценны единообразным UX: список, форма, detail.
- **Варианты:** (a) декларативное UI-дерево, сериализуемое в JSON-RPC
  (как `@raycast/api`), (b) отдельный webview на плагин, (c) только текстовый
  вывод.
- **Выбор:** (a) — плагин описывает `List/Form/Detail/Action`, SDK на стороне
  плагина (React-подобный reconciler) сериализует дерево, хост рендерит его
  в общем UI.
- **Обоснование:** единый look&feel; безопасность (плагин не исполняет
  произвольный JS в UI-процессе); компактный протокол.
- **Последствия:** ограниченная выразительность; запасной клапан — панель
  Detail с markdown-превью, рендерящаяся в песочнице.

**Решение 5: Поиск — in-memory индекс в Rust + SQLite FTS5 для файлов**
- **Контекст:** отклик поиска должен быть < 20 мс на десятках тысяч записей.
- **Варианты:** (a) всё в SQLite (LIKE/FTS5), (b) in-memory fuzzy-индекс
  (алгоритм fzf-like) + SQLite как персистентный кэш, (c) интеграция с
  Everything SDK.
- **Выбор:** (b); приложения/команды/настройки — целиком в памяти; файловый
  индекс — инкрементальная индексация папок пользователя в SQLite FTS5;
  если установлен Everything — опциональный провайдер полнотекстового поиска
  по всему диску.
- **Обоснование:** латентность в памяти несравнимо ниже; FTS5 терпим к объёмам
  файлов; Everything бесплатно решает «глобальный» поиск без наших затрат на
  индексацию всего диска.
- **Последствия:** два слоя поиска — усложнение агрегации; первичная
  индексация идёт в фоне с индикатором прогресса.

**Решение 6: Хранилище — SQLite (rusqlite) + конфиг-файл**
- **Контекст:** локальные данные: клипборд, сниппеты, кэши индексов, настройки.
- **Выбор:** SQLite через `rusqlite`; миграции — `refinery`; настройки
  пользователя — JSON/TOML в `%APPDATA%/iskra`.
- **Обоснование:** без сервера, транзакции, FTS5 «из коробки».
- **Последствия:** изображения клипборда — в blob с лимитом размера и политикой
  вытеснения (по умолчанию хранить 1000 записей / 200 МБ).

**Решение 7: Интеграция с Windows — windows-rs напрямую, без прослоек**
- **Контекст:** хоткеи, клипборд, управление окнами, автозапуск.
- **Выбор:** `RegisterHotKey` (хоткеи), `AddClipboardFormatListener` (клипборд),
  `SetWinEventHook` + DWM API (окна, фокус), реестр `Run` / Startup Apps
  (автозапуск) — через крейт `windows-rs`; небезопасные блоки изолируются в
  модуле `sys` с безопасными обёртками.
- **Обоснование:** плагины Tauri не покрывают эти сценарии полноценно; прямой
  контроль упрощает отладку квирков (DPI, фокус, fullscreen).
- **Последствия:** обязательные spike-задачи в первой фазе для проверки квирков
  (см. риски).

**Решение 8: Профиль WebView2 — GPU-off в прод-сборке**
- **Контекст:** критерий RAM ≤ 80 МБ; замер фазы 0: 97,9 МБ private WS без
  флагов (доминирует рантайм WebView2, ~6 процессов).
- **Выбор:** `additionalBrowserArgs` = `--disable-gpu --disable-gpu-compositing`
  в прод-сборке; в dev — без флагов.
- **Обоснование:** замер: 64–67 МБ private WS; bench p95 13,5 → 14,1 мс
  (деградация < 1 мс); UI лончера — списки и лёгкие анимации, софтверного
  рендера достаточно.
- **Последствия:** перепроверить анимации/скролл на первом реальном UI (фаза 1);
  при деградации — точечный откат, тогда пересматривается RAM-критерий.

### 4.3. Модель данных

```sql
-- SQLite, ключевые таблицы
plugins(id TEXT PRIMARY KEY, name TEXT, version TEXT, manifest_path TEXT,
        permissions JSON, enabled INTEGER DEFAULT 1, state JSON);

commands(id TEXT PRIMARY KEY,
         plugin_id TEXT NULL,            -- NULL = встроенная команда
         title TEXT, icon TEXT, keywords TEXT,
         mode TEXT CHECK(mode IN ('view','no-view')),
         hotkey TEXT NULL, enabled INTEGER DEFAULT 1);

clipboard_entries(id INTEGER PRIMARY KEY,
                  kind TEXT CHECK(kind IN ('text','image','files')),
                  content BLOB, preview TEXT, pinned INTEGER DEFAULT 0,
                  source_app TEXT, created_at INTEGER,
                  used_at INTEGER, used_count INTEGER DEFAULT 0);

snippets(id INTEGER PRIMARY KEY, name TEXT, body TEXT,
         keywords TEXT, created_at INTEGER);

file_index(path TEXT PRIMARY KEY, name TEXT, ext TEXT,
           mtime INTEGER, size INTEGER);
-- + FTS5-таблица поверх file_index(name)

settings(key TEXT PRIMARY KEY, value JSON);
```

### 4.4. API / Интерфейсы

**Манифест плагина** (поле `wrc` в `package.json`):

```json
{
  "name": "iskra-github",
  "iskra": {
    "title": "GitHub",
    "icon": "icon.png",
    "commands": [
      { "name": "repos", "title": "Мои репозитории", "mode": "view" }
    ],
    "permissions": ["network:api.github.com", "storage"]
  }
}
```

**Протокол хост ↔ плагин** (JSON-RPC 2.0 over stdio):

- хост → плагин: `initialize` (версии, permissions, settings), `onOpen`
  (запуск команды), `onQuery` (текущий запрос → элементы списка), `onAction`.
- плагин → хост: `pushScreen` (сериализованное UI-дерево), `toast`,
  `storage.get/set`, `clipboard.read/write`, `fetch` (проксируется хостом
  с проверкой `permissions`), `setLoading`.

**SDK (JS/TS), эскиз:**

```ts
import { List, Item, Action } from "@iskra-launcher/sdk";

export default async function repos({ query }: CommandArgs) {
  const repos = await github("/user/repos");
  return (
    <List searchBarPlaceholder="Фильтр…">
      {repos.map((r) => (
        <Item key={r.id} title={r.name} subtitle={r.description}
              actions={<Action.Open url={r.html_url} />} />
      ))}
    </List>
  );
}
```

Для MVP допускается упрощённый SDK без JSX: команда возвращает массив `Item` —
механизм сериализации тот же.

**Внутренний интерфейс ядра (Rust):** поисковые источники реализуют трейт —

```rust
trait SearchProvider: Send + Sync {
    fn id(&self) -> &str;
    fn priority(&self) -> u8;
    fn search(&self, query: &str, limit: usize) -> Vec<Hit>;
    fn prefix_search(&self, limit: usize) -> Vec<Hit>; // пустой запрос
}
```

Движок агрегирует хиты всех провайдеров, применяет склейку ранжирования
(fuzzy-score + приоритет провайдера + частота использования).

## 5. Альтернативы (отклонённые)

- **Electron + React:** путь Raycast, fastest MVP и Node «из коробки», но
  ~150+ МБ RAM и ~100 МБ дистрибутив для резидентного приложения — проигрыш в
  главном конкурентном преимуществе. Возврат к варианту, если WebView2
  заблокирует ключевые сценарии.
- **Форк Flow Launcher:** готовая база, но чужой WPF-legacy, C#-плагинная
  экосистема и UX, который мы хотели бы превзойти, а не унаследовать.
- **WinUI 3 / WPF:** лучший нативный вид, но дорогая разработка сложного UI и
  почти нет пути к JS-экосистеме плагинов (главный актив продукта).
- **Flutter Desktop:** системная интеграция через platform channels, слабый
  текстовый ввод/accessibility на desktop, недоступна веб-экосистема.
- **UWP:** тупиковая платформа Microsoft.

## 6. Риски и смягчение

| Риск | Вероятность | Влияние | Смягчение |
|------|------------|---------|-----------|
| Квирки Windows API: фокус/DPI/клипборд-форматы/fullscreen ведут себя не как в доках | Высокая | Среднее | Spike-задачи в фазе 0 до старта основных работ; прототип окна и клипборда за первую неделю |
| Cold start экосистемы плагинов («нет плагинов → нет пользователей») | Высокая | Высокое | 5–8 first-party плагинов в MVP; установка из git-репо без централизованного store; простой гайд публикации |
| Дистрибутив растёт из-за бандла Node-рантайма | Средняя | Низкое | Node 22 SEA (single executable); замер в фазе 0; фолбэк — требовать системный Node |
| SmartScreen/антивирусы на глобальные хуки и автозапуск | Средняя | Среднее | Код-подпись сертификатом (EV — позже, после валидации продукта); открытый исходный код ядра снижает недоверие |
| Раздувание скоупа при одиночной разработке | Высокая | Высокое | Жёсткие анти-цели (§3.2); план по фазам с критериями завершения; правило «новая идея → в бэклог, не в MVP» |
| Память WebView2 в простое выше ожиданий | Низкая | Среднее | Замер в фазе 0: 97,9 МБ private WS без флагов; с GPU-off (решение 8) — 64–67 МБ; перепроверить на реальном UI с анимациями |
| Raycast выйдет на Windows | Низкая | Высокое | Скорость итераций, фокус на Windows-специфике (клипборд, окна, интеграция), которую кроссплатформенный конкурент сделает позже |
| Тёзки: Iskra Text Editor (MS Store, редактор), Iskra d.d. (электроника, ЕС) | Средняя | Низкое | Категорийная дистанция (лончер ≠ редактор); везде позиционировать «Iskra — launcher»; полноценный trademark-поиск перед коммерциализацией |

## 7. Открытые вопросы

- **Лицензия и открытость:** open-source ядро (MIT/Apache-2.0) или
  проприетарное? Влияет на доверие, вклад сообщества и монетизацию.
- **Node-рантайм:** ~~бандлить (SEA, +~50 МБ) или требовать установленный Node с
  понятным онбордингом?~~ **Решено 2026-09-29 (фаза 0):** требуем установленный
  Node; SEA — запасной путь (+87,5 МБ, несовместим с лимитом 20 МБ).
- **Windows 10:** поддерживать ли с WebView2-bootstrapper после MVP?
- **Монетизация:** freemium (синхронизация, командные фичи, темы) — подтвердить
  гипотезу после MVP.
- **Не-JS плагины:** нужен ли Python-SDK в v1 (протокол позволяет; решение —
  по спросу).
- **Домен:** свободны `iskra.tools` и `iskralauncher.com` — зарегистрировать до
  любого публичного анонса; `iskra.app` (парковка Afternic) — кандидат на выкуп
  через брокера.

## 8. Критерии готовности

- [ ] `Alt+Space` → окно отрисовано: p95 < 100 мс на эталонном железе
      (i5-класс, SSD, Win 11)
- [ ] RAM в простое ≤ 80 МБ (shell + host без плагинов; профиль GPU-off —
      решение 8), инсталлятор ≤ 20 МБ (Node не бандлим — §7)
- [ ] Поиск: < 20 мс отклик на 10 000 записей, плавные 60 FPS при скролле
- [ ] Клипборд: история до 1000 записей (текст + изображения), поиск и pin,
      данные переживают перезагрузку
- [ ] Окно скрывается при потере фокуса; корректно поверх fullscreen-приложений
- [ ] Window management: 6 команд (left/right half, maximize, move to next
      monitor, center, restore) работают в основных сценариях (в т.ч. с UWP-окнами)
- [ ] 5 first-party плагинов установлены и работают: npm search, GitHub, emoji,
      перевод, kill-process
- [ ] Плагин с бесконечным циклом не блокирует UI (таймаут + kill процесса);
      падение плагина показывает toast и не роняет лончер
- [ ] Плагин без permission `clipboard.read` получает ошибку при попытке чтения
      клипборда (проверка модели разрешений)
- [ ] Автозапуск, трей, переназначение глобального хоткея и светлая/тёмная темы
      работают из настроек
