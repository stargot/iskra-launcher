# Спайк: tauri-app — Tauri 2 shell, frameless-окно, глобальный хоткей, латентность показа

Снятие риска фазы 0 по `docs/specs/2026-09-17-windows-raycast-clone-spec.md`, §4.2 решения 1 и 7.
Окружение: Windows 11, VS2022 (vcvars64), Tauri 2.11, пакет `wrc-spike`. Дата: 2026-09-29
(первый прогон 2026-09-17 не дошёл до замеров — см. «Хоткеи и история падения»).

## Что проверялось

- Релизная сборка после переезда проекта из `D:\Projects\wrc` в `D:\Projects\Iskra`
  (cargo clean + пересборка через `build.cmd`).
- Латентность «нажатие глобального хоткея → окно показано и в фокусе» (полный системный
  путь: SendInput реальных клавиш → RegisterHotKey → handler).
- RAM: главный процесс + дерево дочерних `msedgewebview2` (WebView2-рантайм).
- Регистрация хоткеев: устойчивость к занятому хоткею (не ронять приложение).

## Методика

- Бинарь: `target/release/wrc-spike.exe` (профиль release, `windows_subsystem = "windows"`).
- Bench-режим `--bench N`: приложение само шлёт `Ctrl+Alt+F9` через SendInput (реальные
  системные события), окно скрывается между итерациями (мерится путь hidden → shown),
  латентность пишется в `latency.log` как микросекунды от входа в обработчик до
  `set_position` + `show` + `set_focus`.
- RAM: `Start-Process` → ожидание 8–10 c → дерево процессов через `Win32_Process`
  (ParentProcessId от главного pid) → сумма WorkingSet и Private Working Set
  (`Win32_PerfFormattedData_PerfProc_Process.WorkingSetPrivate`; Private WS — метрика
  как в диспетчере задач, без двойного учёта разделяемых страниц). После замера процесс
  и его webview-потомки убивались.
- p95 — nearest-rank (как в ext-host).

## Сборка

- После переезда проекта релизная сборка падала: артефакты в `target/` держали абсолютные
  пути `D:\Projects\wrc\...` (build-скрипт Tauri искал permissions по старому пути).
  `cargo clean` + пересборка это лечат — подтверждено.
- Вторая проблема была вне проекта: на машине отсутствовали библиотеки Windows SDK
  (`C:\Program Files (x86)\Windows Kits\10` без `Lib`/`Include`) → `LNK1181: cannot open
  input file 'kernel32.lib'`. Вылечено установкой Windows SDK 10.0.26100 (`winget install
  Microsoft.WindowsSDK.10.0.26100`); vcvars64 после этого подхватил `um`/`ucrt` пути.
  Итоговая сборка: `Finished release profile in 2m 10s` с нуля.

## Латентность показа (Ctrl+Alt+F9 → show+focus), n=50

- **avg = 10.17 мс, p95 = 13.51 мс** (min 6.54, max 15.32, медиана 10.13)

Спека ждала p95 < 150 мс — реальность на порядок лучше (запас ~11×). Полный системный путь
через RegisterHotKey и SendInput укладывается в кадр 60 fps с запасом.

## RAM (прогон 10 c, статический index.html)

- Главный процесс `wrc-spike.exe`: WS 25.9 МБ, private WS 4.8 МБ.
- Дочерние `msedgewebview2`: 6 процессов, сумма WS ~318 МБ, сумма private WS ~93 МБ.
- **Итого по WorkingSet (наивная сумма): ~344–348 МБ** — разделяемые страницы считаются
  в каждом процессе многократно.
- **Итого по Private Working Set (честно): 97.9 МБ.**

Целевой ориентир спеки ≤ 80 МБ: private WS превышает на ~20%. Доминирует рантайм WebView2
(GPU-, network-, utility-процессы), а не наше приложение.

### Мини-спайк RAM: флаги WebView2 (2026-09-29, follow-up)

Инструмент: переменная окружения `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` при запуске exe
(аддитивно к аргументам приложения, код не менялся). Замер — тот же (private WS, сумма
dереву процессов, 10 c прогон, статический index.html).

| Комбинация | private WS | примечание |
|---|---|---|
| baseline (без флагов) | 101.7 МБ (повторный прогон; ранее 97.9) | 7 процессов в дереве |
| `--disable-gpu --disable-gpu-compositing` | **64.4 МБ** (повторы 67.1 / 63.9) | лучший, стабильный |
| `--renderer-process-limit=1 --process-per-site` | 99.3 МБ | эффекта почти нет |
| все четыре флага вместе | 66.6 МБ | no-gpu доминирует, лимиты не добавляют |

Контрольный bench `--bench 50` с лучшей комбинацией: **avg = 11.01 мс, p95 = 14.13 мс**
(без флагов 10.17 / 13.51) — деградация ~0.6–0.9 мс, незаметна; p95 остаётся на порядок
ниже лимита 150 мс.

**Вывод: ≤ 80 МБ достижимы** (`--disable-gpu --disable-gpu-compositing` → 64–67 МБ private WS),
ценой софтверного рендера. На статическом UI цена нулевая; риск — латентность анимаций/скролла
на богатом UI, требует перепроверки на первом реальном UI фазы 1. Лимиты процессов
(`--renderer-process-limit`, `--process-per-site`) на одностраничном лончере эффекта не дают.
Более агрессивные варианты (`--single-process` — нестабилен; API `MemoryUsageTargetLevel=Low`
в WebView2 1.0.2420+) не проверялись.

## Хоткеи и история падения

- Симптом 2026-09-17: `runtime.log` обрывался после «clipboard listener installed», строки
  «hotkeys registered» нет. В коде стояло `register(HOTKEY_SHOW)?` — любая ошибка регистрации
  молча роняла приложение через `?` в setup.
- Сегодня (после cargo clean): **Alt+Space регистрируется успешно** — конфликт с PowerToys Run
  или другой программой НЕ подтвердился. Наиболее вероятная причина старого обрыва — внешнее
  прерывание процесса на старте либо разовая занятость хоткея в тот день; воспроизвести падение
  нельзя, обе гипотезы остались без прямого подтверждения.
- Правка (минимальная, без рефакторинга): ошибки `register()` больше не роняют приложение —
  пишутся в `runtime.log` и stderr; при занятом Alt+Space пробуется фолбэк **Ctrl+Alt+Space**
  (обработчик понимает оба), факт регистрация/фолбэк/отказ фиксируется в логе
  («hotkey registered: Alt+Space», «hotkey registration done»).

## Вердикт по критериям фазы 0

- **Латентность p95 < 150 мс: пройдено** (13.51 мс, запас ~11×).
- **RAM ≤ 80 МБ: пройдено с флагами** `--disable-gpu --disable-gpu-compositing` (64–67 МБ
  private WS при p95 14.13 мс); без флагов 98–102 МБ. Рекомендация — закладывать флаги в прод
  фазы 1 (env `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` или `additionalBrowserArgs` в
  tauri.conf.json), перепроверив анимации на реальном UI.
- **Инсталлятор ≤ 20 МБ: скорее пройдено** (exe 8.84 МБ), но сам инсталлятор не собирался.
- **Устойчивость хоткеев: пройдено** — занятый хоткей больше не убивает приложение, фолбэк
  логируется.

## Что осталось неизвестным

- Размер реального инсталлятора (NSIS/WiX) — не собирался.
- Влияние GPU-off на реальном (анимированном) UI фазы 1 — на статике деградации нет,
  на анимациях не мерилось. Не проверялись: `--single-process` (нестабилен), API
  `MemoryUsageTargetLevel=Low` (WebView2 1.0.2420+), поведение при долгом аптайме.
- Латентность под нагрузкой (работающий браузер, 100+ процессов) и на ноутбуке с гибернацией —
  не мерилась.
- Клипборд-листенер работает (лог пишется), но задержка доставки события в UI не замерялась.
- Mica: лог пишет «applied», визуальная проверка не проводилась.
